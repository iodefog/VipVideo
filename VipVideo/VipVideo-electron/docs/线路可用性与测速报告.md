## 一、判定标准

目标地址拼接方式与 App 完全一致（见 `vipWindow.js`：`target = 线路url + 原始视频url`，不做 encode）。

| 判定 | 含义 | 计分 |
| --- | --- | --- |
| `✅ PASS` | 页面出现 `<video>` 且 `currentTime` 真的在前进，即成功解析并播放 | 1 |
| `⚠️ MEDIA` | 抓到了视频流请求（m3u8/mp4/flv/ts）或有 `<video>` 元素，但未起播（多为 readyState=0） | 0.5 |
| `❌ FAIL` | 无 video 元素、无视频流请求（含预筛阶段的网络不通 / HTTP 错 / 页面明确报错） | 0 |

每条用例先做轻量 HTTP 预筛，明显不可用的直接判 FAIL，只有通过预筛的才启动浏览器实测（本轮 235 条中 116 条在预筛阶段即淘汰）。

## 四、结论与处置建议

**第一梯队（可常态使用，建议排到列表最前）**
`IK9`、`七七云`、`爱豆` —— 三者互补：爱奇艺用「爱豆」，芒果TV 用「七七云/爱豆」，bilibili 用「七七云」，腾讯/优酷用「IK9」。

**第二梯队（稳定 3 分，主四大站可用）**
`CK`、`M3U8`、`PM`、`盘古2`、`虾米`、`虾米2`、`8090`、`HLS`、`闲鱼`、`冰豆` —— 爱奇艺/腾讯/优酷基本通杀；芒果TV 与 bilibili 无效。

**观察名单（有流但脚本里没起播，推荐在 App 内手动验证）**
`纯净1`（5 站全是 MEDIA）、`JX`、`思古3`、`JY`（复测时为 MEDIA）—— 这类通常是 HLS/MSE 或播放器自动安全检查导致 headless 不起播，真实 Electron 窗口里往往能播，不要直接删。

**建议清理（0 分，31 条）**
见上表所有 0 分行。它们多数是域名失效或被墙/被墙式跳转，留着只会让用户反复试错。

## 五、误差说明与复测

1. **芒果TV 样本本身源站就不可播**：直连校验（`node test-parsers.js --direct`）结果为 爱奇艺/腾讯/优酷/bilibili = `PASS`，芒果TV = `FAIL`。因此芒果TV 一列的 FAIL 有相当比例来自样本失效，不能据此认定线路不支持芒果。
2. **bilibili 全线仅「七七云」通过**：bangumi 类链接有 Referer/UA/地域校验，脚本环境比 App 更严格，App 内实际成功率可能更高。
3. **可能存在目标站限流**：本轮短时间内对同一批第三方接口发起了上百次请求，个别接口（如 `邦宁`）在首轮曾 PASS、复测变为 FAIL，属于被限速/临时故障的抖动，不是稳定的不可用。
4. **MEDIA 不等于不可用**：只说明脚本没能让它播起来，需要在 App 里点一次确认。

**复测命令**

```bash
# 全量（低占用推荐）
node test-parsers.js --concurrency=2 --wait=12 --pause=300

# 只测某几条线路
node test-parsers.js --only=虾米,冰豆,七七云

# 关闭图片拦截做复核（排除拦截导致的误判）
node test-parsers.js --only=JY,思古3 --blockimg=false

# 校验测试样本本身是否可播
node test-parsers.js --direct
```

## 六、App 内置「测速」功能

上述能力已内置到应用：点击 **VIP → 测速排序** 即可在当前页面**原地**跑一轮，不跳转、不打断正在看的内容。

- **为什么选后台原地跑**：测速是辅助动作，跳到新页面会打断正在播放的内容、污染历史记录，并且用户测完还得回来手动选线路；原地跑 + 浮层表格可以直接「点一行即用」。
- **实现方式**：`speedTest.js` 在主进程用隐藏 `BrowserWindow` 队列测试（默认并发 2，单条硬超时即销毁窗口），通过 `speed:progress` / `speed:done` 回传；`renderer.js`（主界面）与 `vipWindow.js`（子窗口，经 `child_preload.js` 桥接）负责渲染浮层。
- **交互**：运行时按钮变「停止测速」并显示 `已完成/总数`；完成后弹出排行榜表格（按得分降序、各站点 ✅/⚠️/❌ 矩阵），**点击任意行立即用该线路重新解析当前页面**。
- 结果仅供参考，与上面第五章的三条误差说明同样适用。
